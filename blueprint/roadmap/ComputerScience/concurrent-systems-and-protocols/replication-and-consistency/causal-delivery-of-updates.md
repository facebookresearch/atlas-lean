# Causal delivery of updates

Read an execution of the [Lamport clocks](../lamport-clocks/README.md) model, a finite list of events $e_0, \dots, e_{n-1}$ in which each event belongs to a process and may receive the message of the event at some position, as an execution of a replicated system whose replicas are the processes. An event that receives no message issues a new update, identified with the position of that event, and an event that receives from position $i$ delivers the update issued at position $i$. An update $u_1$ happened before an update $u_2$ when the issue of $u_1$ [happened before](../lamport-clocks/happens-before.md) the issue of $u_2$ in Lamport's sense: a chain of events leads from the issue of $u_1$ to the issue of $u_2$, in which each event is followed by a later event that belongs to the same replica or receives from it.

The execution provides *causal delivery* if every replica delivers an update $u_2$ only after it has delivered every update $u_1$ that happened before $u_2$, where a replica counts the updates it issues as delivered. That is, whenever the event at position $j$, of replica $r$, delivers the update $u_2$ issued at position $i_2$, and the update $u_1$ issued at position $i_1$ happened before $u_2$, some position $k < j$ holds an event of $r$ that either issues $u_1$ ($k = i_1$) or delivers it. This constrains only the order of deliveries within one finite execution: a replica may deliver an update more than once, or never, whereas the reliable causally-ordered broadcast that Shapiro et al. assume also delivers every update exactly once to every replica.

Shapiro et al. define happened-before between updates by delivery: $u_1$ happened before $u_2$ when $u_1$ has been delivered at the replica where $u_2$ originates by the time $u_2$ is issued there. When every receipt names an earlier issue, the transitive closure of this order, in which a replica's own earlier updates count as delivered, is the relation above ([Happened-before between updates, by delivery](happens-before-iff-trans-gen-delivered.md)).

The execution need not be [well formed](../lamport-clocks/well-formed.md), that is, a receipt need not name an earlier position, and happened-before is taken over all of its events. A receipt that names an earlier position holding no issue (an earlier receipt), such as a receipt from a delivery, delivers no update but still adds a step to happened-before. Even on a well-formed execution, causal delivery can then demand more than it would if happened-before between updates were defined by delivery as above. A receipt that names a later issue delivers that update, and is constrained as a delivery, but adds no step to happened-before.
