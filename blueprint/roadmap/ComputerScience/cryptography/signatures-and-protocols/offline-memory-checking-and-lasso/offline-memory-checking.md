# Offline memory checking with timestamps

Consider a memory of cells indexed by addresses, initialized to values $v_a^{0}$, and an execution of $T$ steps in which step $s\in\{1,\dots,T\}$ reads address $a_s$ and then writes a value back to the same address (a pure read writes back the value read). In *offline memory checking* each stored entry is a triple (address, value, timestamp), and the write timestamp is a trusted, strictly increasing global counter, namely the current step number $s$; it is not chosen by the prover. Define multisets of triples: $\mathsf{Init}=\{(a,v_a^{0},0)\}_a$; the read set $\mathsf{RS}$ of the triples $(a_s,v_s,t_s)$ returned by the reads, where the read timestamp $t_s$ must satisfy $t_s<s$; the write set $\mathsf{WS}=\{(a_s,v'_s,s)\}_s$ of the triples written; and $\mathsf{Final}=\{(a,v_a^{\mathrm{fin}},t_a^{\mathrm{fin}})\}_a$, the last entry of every cell. The checker verifies $t_s<s$ for every read and accepts iff $\mathsf{Init}\cup\mathsf{WS}=\mathsf{RS}\cup\mathsf{Final}$ as multisets. Incrementing a timestamp only within each read and write pair does not suffice: it does not order different pairs, so permuting the pairs preserves the multiset equality while changing which write is the latest. For a read-only memory, where every step writes back exactly the value it read, per-cell counts incremented by one on each access suffice instead of the global counter, as in Spark and Lasso; for read/write memory they do not, since reads could then be answered with values written only later.
