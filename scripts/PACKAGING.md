# Distribute Atlas as a Lake package

## Standard dependency workflow

Atlas is already a normal Lake package. The default source distribution is
a Git dependency pinned to a commit, as with Mathlib:

~~~toml
[[require]]
name = "atlas"
git = "https://github.com/facebookresearch/atlas-lean.git"
rev = "<full Atlas commit>"
~~~

Commit the consuming project's resolved `lake-manifest.json` and use the
matching `lean-toolchain`. Then run:

~~~bash
lake update
lake exe cache get
lake build +MathlibExt.Topology.HomogeneousSpace
~~~

`lake exe cache get` fetches Mathlib's artifacts. It does not provide a cache
for Atlas's own modules.

Source and compiled artifacts are separate. The packaging command below
produces **one Lake-native build archive** through `lake pack` by default.
`--offline-bundle` adds a self-contained source/artifact bundle for offline
consumption. Libraries are built once; both formats use that same qualified
build when the extra bundle is requested. Git dependencies remain the normal
source workflow.

`scripts/package_atlas.py` creates a standalone distribution from an exact
committed Atlas revision. It discovers every `[[lean_lib]]` in the root
`lakefile.toml`, including test libraries. Currently the distribution contains
`MathlibExt`, `CSLibExt`, `WantedExt`, `MathlibExtTest`, and `CSLibExtTest`.

The package preserves Atlas's name, module paths, Lake options, dependency
lock, toolchain, and licensing files. Undeclared legacy trees and archived
packages are outside the root distribution. `WantedExt` retains its purpose
of representing deferred implementations.

## Commands

- `build` exports committed sources, builds every declared library, and runs
  Atlas's canonical CI validators before creating the distribution.
- `verify --build-archive` checks a native build asset's trusted SHA-256.
  `verify --archive` checks the optional offline bundle and its individual file
  digests; `verify --directory` checks an installed source tree.
- `install` safely installs into an immutable version directory named by the
  archive's SHA-256. Any downstream Lake project can use that directory.

The native archive contains build artifacts; its source comes from the pinned
Git dependency. The optional offline archive includes source, package metadata,
`atlas-package.json`, and compiled artifacts. Dependency checkouts are excluded.
Offline source is installed read-only; Lake may populate its local build cache.
Hosts with a different OS/architecture rebuild from the same source pin.

Prerequisites: Python 3.11+, Git, elan/Lake, and the selected Lean toolchain.

## Build a qualified distribution

From an Atlas checkout:

~~~bash
git fetch origin main
atlas_revision="$(git rev-parse origin/main)"
mkdir -p dist

python3 scripts/package_atlas.py build \
  --revision "$atlas_revision" \
  --out-dir dist \
  --jobs 32 \
  > dist/package-result.json
~~~

The script reads Git objects at that revision. The validation scripts come
from the packaging checkout and their hashes are recorded. A failed build or
trust check produces no release archive. Outputs are one native `.tar.gz`, a
JSON descriptor, a per-file manifest, checksum metadata, and the build log.
Existing release files are not overwritten; select a new output directory for
another run.

The default is 32 Lean/Lake runtime workers. `--jobs` changes the worker-pool
setting; CPUs are shared by the OS, and dependency ordering and archive
compression affect actual utilization. The manifest records the requested
worker count.

The JSON result includes `lake_build_archive`, `lake_build_archive_sha256`,
and `lake_build_archive_bytes`. `build_manifest` names the source/artifact
index, bound by `manifest_sha256`. The native archive contains only the package
build directory in Lake's format. The `archive` fields are present only when
the offline bundle or a source-only preview is requested.

The stdout result uses local absolute paths for build/install commands. The
descriptor saved for publication uses asset filenames, so its references work
after downloading the files into another directory.

After authenticating the archive and matching its source revision/toolchain,
a consumer can restore it directly:

~~~bash
lake -d .lake/packages/atlas unpack /path/to/atlas-build-archive.tar.gz
lake build +MathlibExt.Topology.HomogeneousSpace
~~~

Its default asset name is generated by Lake, for example
`atlas-x86_64-unknown-linux-gnu.tar.gz`. Publish that asset against its exact
source tag. Automatic GitHub build-cache fetching can be enabled through
Lake's `preferReleaseBuild` setting when the release workflow is configured.

For faster builds, `--dependency-cache /path/to/lake/packages` can reuse
clean dependency checkouts whose revisions match the pinned public lock.
The build can take substantial time on a cold cache.

Read and verify the artifact identities:

~~~bash
atlas_build_archive="$(python3 -c 'import json; print(json.load(open("dist/package-result.json"))["lake_build_archive"])')"
atlas_build_sha256="$(python3 -c 'import json; print(json.load(open("dist/package-result.json"))["lake_build_archive_sha256"])')"

python3 scripts/package_atlas.py verify \
  --build-archive "$atlas_build_archive" \
  --sha256 "$atlas_build_sha256"
~~~

`build --source-only` creates an explicitly unqualified development preview.
Default installation rejects it. `--allow-source-only` is available for local
development; qualified release consumption uses the default checks.

## Optional offline source distribution

Add `--offline-bundle` to the initial build command above to produce this
additional format from the same build. Read its identities from that result:

~~~bash
atlas_archive="$(python3 -c 'import json; print(json.load(open("dist/package-result.json"))["archive"])')"
atlas_sha256="$(python3 -c 'import json; print(json.load(open("dist/package-result.json"))["archive_sha256"])')"

python3 scripts/package_atlas.py verify \
  --archive "$atlas_archive" \
  --sha256 "$atlas_sha256"
~~~

Then install the offline archive into the project's ignored Lake cache:

~~~bash
cd /path/to/my-project
mkdir -p .lake

python3 /path/to/atlas-lean/scripts/package_atlas.py install \
  --archive "$atlas_archive" \
  --sha256 "$atlas_sha256" \
  --into .lake/atlas \
  > .lake/atlas-install.json
~~~

Add the installed path to the project's `lakefile.toml`:

~~~toml
[[require]]
name = "atlas"
path = ".lake/atlas/<archive-sha256>"
~~~

Use the release's `lean-toolchain` and align shared dependency versions with
its public lock. Give the downstream project's own libraries distinct
top-level module roots. Each released Atlas root needs one provider.

Then resolve dependencies and import a public module:

~~~bash
lake update
lake exe cache get
lake build +MathlibExt.Topology.HomogeneousSpace

printf '%s\n' 'import MathlibExt.Topology.HomogeneousSpace' > .lake/atlas-smoke.lean
lake env lean .lake/atlas-smoke.lean
~~~

The install result contains a generic `atlas-consumer-lock/1` record with the
source revision, archive/manifest/source digests, toolchain, dependency lock,
and library list. Save that record in the project's dependency lock so another
machine can install the same artifact.

Verify installed sources using the manifest digest from that trusted lock:

~~~bash
python3 /path/to/atlas-lean/scripts/package_atlas.py verify \
  --directory ".lake/atlas/$atlas_sha256" \
  --manifest-sha256 "<trusted-manifest-sha256>"
~~~

Build outputs can change as Lake rebuilds; installed-source verification checks
the immutable source/configuration inputs and rejects added or modified sources.

## Publish and consume releases

Build and qualify the exact intended revision. Upload the native archive,
descriptor, and digest/index metadata into a draft GitHub release. Include the
offline bundle if requested. Publish with immutable releases enabled after
its assets are complete.

### Publish through the GitHub website

1. Choose a new release version and set `version` in `lakefile.toml` to match
   it. For example, tag `v2.0.0` corresponds to package version `2.0.0`.
2. Merge the packaging/version changes into `main` and wait for CI. Build that
   exact committed revision with the command above and verify its outputs.
3. In repository **Settings → General → Releases**, enable release immutability.
4. Create a tag at the full `source_revision` recorded in the build result.
   The following example uses `v2.0.0`; choose the version from step 1:

   ~~~bash
   atlas_release_tag="v2.0.0"
   atlas_revision="$(python3 -c 'import json; print(json.load(open("dist/package-result.json"))["source_revision"])')"
   git tag -a "$atlas_release_tag" "$atlas_revision" -m "Atlas $atlas_release_tag"
   git push origin "$atlas_release_tag"
   ~~~

5. Open the repository's **Releases → Draft a new release**, choose that
   existing tag, and enter a title and release notes. Include the Lean version,
   dependency pins, included libraries, and any API migration information.
6. Attach the native archive named by `lake_build_archive`, its `.sha256`
   sidecar, the generated `atlas-<commit>-<platform>.json` descriptor, and the
   `build_manifest` JSON index. This is one compressed archive plus metadata.
7. Save the draft, confirm its tag and complete asset list, then publish it.
   A stable release can be marked latest; a candidate should be a prerelease.

Published immutable releases lock the associated tag and uploaded assets.
Complete the uploads while the release is a draft. Subsequent changes require
a new version/tag and a new qualified artifact.

Consumers verify the release and explicit uploaded assets using
`gh release verify` and `gh release verify-asset`. The expected digest comes
from an authenticated descriptor or other trusted release record. A checksum
sidecar fetched from an untrusted location does not authenticate a release.
GitHub's generated source ZIP/tarball is not an attested uploaded asset.

The packaging script does not publish GitHub releases. It supplies the
qualified distribution for a release workflow.

## Format and validation

The current format uses a bounded per-file manifest and local archive
installation. Large distributions should use coherent components and sharded
indexes; GitHub release assets must stay below its per-asset size limit.
Rebuilding or changing an upstream revision creates a new artifact identity.

Run the transport regressions with:

~~~bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover \
  -s scripts -p test_package_atlas.py -v
~~~

## Relationship to Mathlib's practices

Mathlib uses ordinary Git/Lake source pins and a separate per-module cache.
Its cache key mixes source/path, toolchain/configuration, and import hashes.
Trusted CI publishes artifacts; consumers retrieve them with
`lake exe cache get`.

Atlas follows the source/cache separation and reuses its existing
`scripts/check.sh build` validators. The current native archive is a coarser
whole-package cache. Large-scale per-artifact distribution should use Lake's
generic cache facilities rather than copying Mathlib's repository-specific
cache service and upload code.

References: [Mathlib cache documentation](https://github.com/leanprover-community/mathlib4/blob/master/Cache/README.md),
[cache hashing](https://github.com/leanprover-community/mathlib4/blob/master/Cache/Hashing.lean),
and [Lake packaging](https://github.com/leanprover/lean4/blob/v4.35.0/src/lake/README.md).
